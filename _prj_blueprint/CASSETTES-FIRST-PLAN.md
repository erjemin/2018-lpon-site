# Кассеты и MD первыми: план ручного ввода и проверки бизнес-процесса

**Дата и время составления:** 2026-11-21 11:20
**Статус:** план. Документ уточняет порядок работ из `_planstep_for_cassettes.md` (тот писался до решения о конфиге TOML). Код не менялся.
**Связанные документы:** `lpon--metadata-config.md` (формы кассеты и MD), `STOCK-LOCATIONS.md` (где лежит экземпляр), `STATELESS-ORDERS.md` (заказ), `DATA-SOURCES-PARSING.md` (парсинг откладывается).

---

## 1. Решение и причина

Первыми наполняются разделы **кассет** и **MD**. Причины:

1. Все экземпляры собственные, внешнего каталога кассет нет. Парсить нечего, значит данные вносятся вручную.
2. Позиции абсолютно уникальные: один экземпляр, одно состояние, одно место хранения. Это самый простой случай для проверки всего бизнес-процесса «внести, найти, продать, отправить».
3. Вводить придётся сотни записей руками. Значит, форма ввода получает реальную нагрузку и сразу показывает, каких ключей не хватает в конфиге метаданных. Это именно тот сценарий, ради которого конфиг сделан развиваемым («по мере наполнения каталога упорядочивать»).
4. Тот же подход для MD (их тоже много). Кассеты и MD вместе покрывают оба «лёгких» носителя из реестра форм (`item-cassette`, `item-minidisc`, `offer-cassette`, `offer-common` в `config/metadata-toml/default.toml`).

Винил, CD и парсинг прайсов идут после. Они проверяют другую часть системы (импорт и сопоставление), а не бизнес-процесс.

## 2. Что в коде есть, чего нет (сверено 2026-11-21)

| Что нужно для ввода | Состояние |
|:---|:---|
| Модели `TbItem` (релиз) и `TbOffer` (экземпляр), формат `Format.REC_CS` (`cs`), `Format.USE_CS` (`uc`), `Format.REC_MD` (`md`), `Format.USE_MD` (`ms`) | есть |
| Коды экземпляра `TbOffer.s_offer_code` (hashids, создаётся автоматически) | есть |
| Состояния носителя и обложки (`Condition`) | есть, но градации `VG+` и `G+` отсутствуют (см. `DATA-SOURCES-PARSING.md`, раздел 5) |
| Проверка дубликатов артистов, лейблов, стилей | есть (`REFERENCE_ENTITIES_PATTERN.md`) |
| Фото экземпляра (`TbImageMetadata`, `filer`) | есть |
| Формы характеристик кассеты и MD по конфигу | **нет**: загрузчика конфига и виртуальных полей админки нет, пока JSON приходится писать вручную |
| Складские места и перемещения | **нет** (`STOCK-LOCATIONS.md`) |
| Статус экземпляра («в продаже», «забронирован», «продан», «в коллекции») | **нет**, есть только `i_offer_quantity` и `b_offer_is_preorder` |
| Публичная витрина кассет | заглушки: временная вьюха `catalog`, DSL-хабы не реализованы (`DSL.md`) |
| Заказ и корзина | нет (`STATELESS-ORDERS.md`) |

Особенности модели, которые заденут ручной ввод:

- `TbOffer.k_offer_to_source` обязателен в админке (`null=True`, но без `blank=True`; в справке сказано «обязательно»). Для своих кассет нужны «свой» продавец и «свой» источник. Предлагаю один раз завести продавца «LPON (собственный склад)» типа `SellerType.SELLER` и источник типа `SourceType.OTHER` («ручной ввод» уже описан в константе). Это решает и вопрос из `DATA-SOURCES-PARSING.md`: признак «свой склад» пока достаточно держать как договорённость, отдельное поле позже.
- `l_offer_condition_media` по умолчанию равно `Condition.S` («запечатано»). Для б/у кассеты это неверное значение по умолчанию: легко забыть сменить. Нужен либо другой default, либо обязательный выбор.
- `TbOffer.k_offer_to_item` необязателен (`blank=True`, `null=True`). Для абсолютно уникальной записи без известного релиза (самодельная запись, концертная запись с радио) можно создавать оффер без `TbItem`. Решение за владельцем: допускать ли такие офферы или всё равно создавать `TbItem`-«запись».
- `TbOffer.s_offer` обязательный, до 128 символов; формат названия задан в `help_text` («Abbey Road (LP) AnTrop NM/NM (МЗГ)»). Для массового ввода название стоит генерировать автоматически из ключевых полей.

## 3. Модель «один экземпляр, один оффер»

Для кассет и MD принимаем:

- Один физический экземпляр это один `TbOffer`. Даже если есть две копии одного релиза: у каждой своё состояние, комплектация, место хранения и цена.
- `TbItem` описывает релиз или модель (характеристики, общие для всех копий): артист, название, год, `media_format`, цвет корпуса, тип ленты. Копии одного релиза ссылаются на один `TbItem`.
- `i_offer_quantity` для экземпляра равно 1 при наличии и 0 после продажи. Это согласуется с логикой `TbOfferHistory` (запись при изменении количества).
- Для «чистых» носителей под запись (`USE_CS`, `USE_MD`) и для партии одинаковых новых кассет (запечатанные, 10 штук одной модели) возможно количество больше 1. Это отдельный случай, на уникальных экземплярах его пока не проверяем.

Ключи, которые относятся к экземпляру (состояние, комплектация, запись на ленте), живут в `j_offer_metadata`, а к модели (цвет корпуса, тип ленты, хронометраж) в `j_item_metadata`. Распределение уже описано в `lpon--metadata-config.md`.

## 4. Жизненный цикл экземпляра (предложение)

Сейчас статуса нет. Предлагается явное поле `TbOffer.l_offer_status` (набор значений в `constants.py`, как остальные перечисления):

| Статус | Смысл | Видно в публичном каталоге |
|:---|:---|:---|
| `draft` | внесён, данные неполные | нет |
| `collection` | в личной коллекции, не продаётся (в том числе записи из Discogs) | нет |
| `ready` | готов к публикации | нет |
| `for_sale` | в продаже | да |
| `reserved` | забронирован покупателем | да, с пометкой |
| `sold` | продан, ждёт отправки | нет |
| `shipped` | отправлен | нет |
| `withdrawn` | снят с продажи, списан | нет |

Для публичного каталога опубликованность `b_article_published` связанной статьи остаётся отдельным признаком (витрина статьи), а `l_offer_status` управляет жизнью самого экземпляра. Как эти два признака связаны (например, `sold` автоматически снимает с публикации), на решение владельца. Статус `sold` должен совпасть с `i_offer_quantity = 0`; рассогласование сейчас никто не проверяет.

Место хранения отдельно (`STOCK-LOCATIONS.md`), причём виртуальные места `TRANSIT` и `SOLD` дублируют часть статусов. Это сознательно: статус отвечает на вопрос «что с товаром», место на вопрос «где он».

## 5. Сквозной бизнес-процесс для проверки

Цель: пройти путь от кассеты на полке до отправленной посылки на малой выборке (10-20 кассет и 5-10 MD) и записать, где процесс ломается.

| Шаг | Действие | Что нужно в системе | Состояние |
|:---|:---|:---|:---|
| 1 | Внести кассету: артист, название, формат, состояние, комплектация, цвет корпуса, фото | форма `item-cassette` и `offer-cassette` по конфигу | нужен загрузчик конфига |
| 2 | Присвоить код `s_offer_code` | автоматически при создании | есть |
| 3 | Присвоить место хранения | `TbLocation`, поле места | нет |
| 4 | Напечатать этикетку | страница печати | нет |
| 5 | Положить на место, отметить | перемещение (`TbStockMove`) | нет |
| 6 | Опубликовать в каталоге | витрина кассет (простой список) | временная вьюха |
| 7 | Принять заказ | почта или форма; позже корзина | почта (план) |
| 8 | Собрать заказ | лист сборки по местам | нет |
| 9 | Отправить, внести трек-номер | статус `shipped` | нет |
| 10 | Закрыть: количество 0, место `SOLD` | автоматически | нет |

Для первого прогона достаточно шагов 1, 2, 6 и 7 по почте. Шаги 3-5 и 8-10 добавляются по мере появления моделей.

## 6. Удобство ручного ввода

Ввод сотен записей решает судьбу проекта: если это мучительно, каталог не наполнится. Что стоит сделать в админке:

1. **Кнопка «Сохранить и добавить такую же»**. Копирует выбранные поля предыдущей записи (производитель, тип ленты, состояние) в новую.
2. **Пакетный режим для серии**: одни и те же значения для нескольких кассет одной коробки или партии.
3. **Значения по умолчанию из конфига** (`default` в TOML). Для кассеты это `Condition` не `Still Sealed`.
4. **Автоматическое название** `s_offer` из ключевых полей: артист, название, формат, состояние, цвет корпуса.
5. **Подсказки артистов, лейблов и стилей** с проверкой синонимов. Уже есть, но нужно оценить скорость на реальной базе.
6. **Загрузка фото пачкой** с телефона, привязка к экземпляру.
7. **Простой отчёт «что внесено»**: сколько записей в каждом статусе, у скольких нет фото, у скольких нет места.

Все пункты, кроме 1-2, зависят от загрузчика конфига.

## 7. Как проверять результат

После ввода пробной партии (предлагаю 50 кассет и 20 MD):

- Сколько новых ключей понадобилось сверх `default.toml`. Каждый новый ключ добавляется в конфиг с полем `since` (`lpon--metadata-config.md`).
- Сколько секунд занимает ввод одной записи; что именно тормозит.
- Не нашлось ли записей, которые не укладываются в модель (самодельные записи без артиста, сборники, сеты из нескольких кассет).
- Можно ли найти экземпляр по месту и по коду.
- Совпадают ли названия, сгенерированные автоматически, с тем, что хочется видеть.

Результаты записать в блюпринт: они определят, правильно ли устроена схема метаданных.
