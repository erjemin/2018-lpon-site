## 1. Принятые решения

| Вопрос | Решение |
|:---|:---|
| Формат конфига | **TOML** |
| Роль конфига | единый реестр имён ключей и значений `j_item_metadata` и `j_offer_metadata`; формы админки лишь один из потребителей |
| Где лежит | каталог `config/metadata-toml/` рядом с `config/nginx/` |
| Базовый конфиг | `config/metadata-toml/default.toml`: в git, в образе Docker, в проде попадает на хост |
| Рабочие редакции | файлы в том же каталоге (`ACTIVE`, `revisions/`, `journal.jsonl`): не в git, не в образ |
| Хранение | файлы, а не таблица БД: каталог `config` монтируется в контейнер как том |
| Переключатель формата в `TbItem` | ключ `media_format` в `j_item_metadata` (вариант Б), поле `s_item_type` в модель не добавляется |
| Рост конфига | только добавляющие правки, вместо удаления `deprecated` |

## 2. Решение: формат TOML

Причины выбора:

- компактно и читается человеком;
- комментарии прямо в файле (и для оператора, и для истории решений);
- чтение стандартным модулем Python 3.12 `tomllib`, без зависимостей;
- таблицы `tomllib` возвращает в порядке записи, поэтому порядок полей формы сохраняется.

Как работаем с файлом:

- **Читаем** через `tomllib.loads()`, затем собственная проверка схемы (п. 7.4).
- **Записываем** текст как есть: редактор в админке и загрузка файла отдают строку, она сохраняется без разбора и повторной сериализации. Комментарии и оформление не теряются. Пакет `tomlkit` не нужен.

Справка: [Python `tomllib`](https://docs.python.org/3/library/tomllib.html).

## 3. Роль конфига

Конфиг нужен не только для построения форм. Всё, что пишет админка, импорт и парсеры, обязано называть ключи и значения так, как записано в конфиге.

- Имя ключа определяется один раз, в одном месте. Нет `shell_color` в одном месте и `body_color` в другом.
- Форма, фильтр каталога, парсер и отчёты читают один и тот же реестр.
- Конфиг заранее не бывает полным: сначала несколько полей, потом больше, по мере заполнения каталога кассетами. Отсюда возможность править его без выкладки кода.

## 4. Откуда взялись идеи (прототип в TOML)

| Идея из исходного прототипа | Как выражается в TOML |
|:---|:---|
| `app` / `model` / `metadata` | `target = "frontend.TbItem"` и `metadata = "j_item_metadata"` |
| `if s_item_type is "media-cc"::` | `when = { media_format = ["cs", "uc"] }` на форме или на поле |
| `field: body_color [ru:..., en:..., tr:..., am:...]` | `label = { ru = "...", en = "...", tr = "...", am = "..." }` |
| `value: black [ru:..., en:...]` | подтаблица `[form.fields.<поле>.values]`, ключ значения является машинным кодом |
| `value: __any__` | `allow_other = true`: разрешён ввод своего значения, которого нет в списке |
| Одинаковый `body_color` для кассеты и MD | общий справочник `[dictionaries.shell_color]` и `values_from = "shell_color"` |
| Порядок полей в файле | сохраняется (см. п. 2) |

Что исправлено при переносе в `default.toml`:

- армянские подписи цветов в прототипе были сдвинуты на одну позицию (`black` подписан как «прозрачный» и т. д.), часть турецких подписей была неточна; **все переводы tr и am нужно проверить носителем языка**;
- значения без ключа (строки `value: [ru:на_клей, ...]`) запрещены: ключ значения хранится в метаданных, он обязателен и стабилен, подпись можно менять.

## 5. Расхождения с кодом

- В `TbItem` нет поля `s_item_type`. Тип и формат лежат в `j_item_metadata` под ключами `media_type` и `media_format` (`constants.py`, `get_item_metadata_default()`). Принят вариант Б: `media_format` описан в конфиге как первое поле формы без `when`, значения берутся из перечисления `Format`. К полю модели можно перейти позже, если понадобится фильтрация в БД без JSON.
- У `TbOffer` формат хранится в `l_offer_to_format` (перечисление `Format`). Кассета: `cs` (с записью) и `uc` (чистая или б/у под запись). MD: `md` и `ms`.
- Ключ `body_color` не совпадает с существующей константой `KEY_ITEM_SHELL_COLOR = 'shell_color'`. Нужно выбрать одно имя (открытый вопрос).
- Перечисление `ShellColor` (`smoke`, `clear`, `amber` ...) дублирует справочник значений. При переходе на конфиг источником истины становится конфиг, `ShellColor` можно оставить только как стартовый набор. Изменения в `models.py` и `constants.py` в рабочей копии сейчас временные и в git не отправляются.

## 6. Структура файла `default.toml`

Полный пример: `config/metadata-toml/default.toml`. Здесь только словарь схемы.

| Ключ | Где | Смысл |
|:---|:---|:---|
| `version` | корень | версия схемы файла (формат), не номер редакции |
| `languages`, `fallback` | корень | языки подписей и язык по умолчанию; нехватка перевода не ошибка |
| `[dictionaries.<имя>]` | корень | общий справочник значений |
| `[[form]]` | корень | форма: `id`, `target`, `metadata`, необязательные `when` и `title` |
| `[form.fields.<ключ>]` | форма | поле; **ключ таблицы и есть ключ в JSON** |
| `type` | поле | `choice`, `multichoice`, `bool`, `text`, `slug` |
| `label`, `help` | поле | подпись и подсказка на нескольких языках |
| `values` / `values_from` | поле | значения: своя таблица, справочник (`"shell_color"`) или перечисление проекта (`"enum:Format"`) |
| `allow_other` | поле | разрешён ввод значения вне списка |
| `when` | форма или поле | условие показа |
| `grade` | `multichoice` | для каждого пункта можно указать состояние |
| `unit`, `multiline` | поле | единица измерения; многострочный текст |
| `public`, `filter` | поле | показывать в карточке; использовать как фильтр каталога |
| `deprecated` | поле, значение | скрыто из формы, данные остаются |
| `since`, `note` | поле | когда ключ появился; заметка оператору (необязательные) |
| `renamed_from` | поле | прежнее имя ключа (для явной миграции данных, п. 8) |

## 7. Правила схемы

### 7.1 Условия `when`

- Имя в `when` ищется сначала среди настоящих полей модели (`l_offer_to_format`), затем среди полей конфига этой модели (`media_format`, `is_recorded`).
- Несколько ключей в одной таблице означают «и». Список значений означает «любое из».
- Условие на форме скрывает всю группу полей, условие на поле скрывает только это поле.
- Исполняемого кода в условиях нет: только сравнение на равенство и принадлежность списку.

### 7.2 Хранение значений

- Значение лежит в JSON плоским ключом: `{"body_color": "black"}` (как существующие `tape_type`, `packaging`, `inlay_condition`).
- Выбор из списка хранит ключ значения. Если включён `allow_other` и введено своё значение, хранится введённая строка: код отличает его по отсутствию в `values`.
- Пустое значение не записывается: ключ просто отсутствует. Пустая строка, `null` и «выдуманное» значение не пишутся.
- `multichoice` хранит список ключей. При `grade = true` хранится словарь `{"insert": {"condition": "vg"}}` (как `extras` в `metadata_architecture.md`).
- При смене переключателя (например, `media_format`) значения полей прежней формы не удаляются: они скрываются и не проверяются.

### 7.3 Один ключ в разных формах

Один и тот же ключ в разных формах одной модели допустим (`body_color` у кассеты и MD), но тип должен совпадать. Загрузчик отклоняет конфликт. Ключи значений никогда не переиспользуются под другой смысл.

### 7.4 Проверка конфига при загрузке

- `tomllib.loads()`, затем небольшая собственная проверка схемы без внешних библиотек.
- Проверяется: уникальность `id` форм; существование `target` и `metadata` среди моделей и JSON-полей проекта; корректность `values_from` (справочник из конфига или перечисление из разрешённого списка); допустимость `type`; ссылки в `when`; формат имён ключей `^[a-z][a-z0-9_]{1,40}$`.
- Нехватка перевода даёт предупреждение, а не ошибку.

## 8. Как конфиг растёт

Оператор вносит в каталог кассету и понимает, что нужного поля нет. Цикл:

1. Временно записывает значение в «сыром» JSON-редакторе под рабочим ключом.
2. Отчёт **«ключи вне конфига»** показывает ключи и значения из реальных записей, которых нет в конфиге, и число записей. Это материал для решения: добавить в реестр, переименовать или привести к существующему.
3. Оператор правит конфиг, проверяет отличия и активирует.

Правила правок (всегда добавляющие):

| Что изменилось | Что делать | Влияет на данные? |
|:---|:---|:---|
| Новое поле или значение | Просто добавить | Нет |
| Другая подпись, перевод, подсказка | Править текст | Нет |
| Поле или значение больше не нужно | `deprecated = true`, не удалять | Нет, данные остаются |
| Смысл или формат значения изменился | Новый ключ, старый в `deprecated` | Нет |
| Ключ назван неудачно | Отдельная команда переименования с `--dry-run` | Да, только по явному запуску |

- Ключи и значения не удаляются из конфига, пока встречаются в данных. Проверка при активации предупреждает: «ключ `X` удалён из конфига, но найден в N записях».
- Ключ после появления в данных не переименовывается «на лету». Переименование описывается записью `renamed_from` и применяется только отдельной командой.

## 9. Хранилище: файлы в `config/metadata-toml/`

### 9.1 Раскладка

```text
config/
  nginx/                           # уже есть
  metadata-toml/
    default.toml                   # базовый конфиг: в git и в образе
    ACTIVE                         # одна строка: номер активной редакции (не в git)
    revisions/
      0005.toml                    # текст конфига как есть, с комментариями
      0005.meta.json               # когда, кто, источник, комментарий, sha256
      0006.toml
      0006.meta.json
    journal.jsonl                  # журнал действий: активация, откат, сброс
    .lock                          # служебный файл блокировки
```

- **Источник истины для сайта** — `revisions/<номер>.toml`, на который указывает `ACTIVE`.
- Если `ACTIVE` нет (чистая установка), при первом обращении создаётся редакция `0001.toml` из `default.toml`, а `ACTIVE` получает значение 1. Если `default.toml` не читается, приложение работает без форм по конфигу (п. 11).
- Обновление кода и перезапуск контейнера существующие `ACTIVE` и редакции не трогают. Обновление `default.toml` в git не меняет работающий сайт само: оператор видит различие и решает, брать ли его (п. 10, «Сбросить из default.toml»).
- Путь задаётся настройкой `METADATA_CONFIG_DIR` в `settings.py`, по умолчанию `BASE_DIR.parent / 'config' / 'metadata-toml'` (`BASE_DIR.parent` — корень репозитория), с переопределением через `.env`. Тесты подставляют временный каталог.

### 9.2 Как процессы узнают об изменении

Приложение работает в нескольких процессах (gunicorn), общего кэша нет. Процесс держит в памяти разобранный конфиг и пару `(mtime_ns, size)` файла `ACTIVE`. На каждый запрос, которому нужен конфиг, делается один `os.stat(ACTIVE)`. Если пара изменилась, процесс перечитывает `ACTIVE` и нужную редакцию. Запрос к БД и перезапуск контейнера не нужны.

### 9.3 Безопасная запись

1. Взять эксклюзивную блокировку на `.lock` (`fcntl.flock`).
2. Сверить номер редакции, на которой оператор начал правку, с текущим `ACTIVE`. Не совпало: предупреждение (оптимистичная блокировка).
3. Записать `revisions/NNNN.toml` и `NNNN.meta.json` во временные файлы в той же папке и переименовать через `os.replace`.
4. **Последним** обновить `ACTIVE` тем же способом: читатель видит либо старую редакцию, либо новую целиком.
5. Удалить редакции старше последних N (предложено: активная и 2 предыдущие).
6. Дописать строку в `journal.jsonl`.
7. Снять блокировку.

Откат создаёт новую редакцию с текстом предыдущей, история не теряется.

### 9.4 Git и Docker

- Правила в `.gitignore` и `.dockerignore` одинаковые: каталог `config/metadata-toml/` исключается целиком, кроме `default.toml`. Рабочие редакции не попадают ни в репозиторий, ни в образ.
- В проде `default.toml` должен оказаться на хосте в смонтированном каталоге `./config`. Это решается при доработке Docker (аналогично тому, как скрипт запуска уже раскладывает конфиг nginx). Docker-часть проекта сейчас очень предварительная и этим документом не проектируется.
- Права: процесс Django должен иметь право писать в `config/metadata-toml/` на сервере. Проверить при настройке прода.
- `flock` ненадёжен на NFS. Для обычного bind mount на диск сервера это не проблема.
- Резервная копия: включить `config/metadata-toml/` в то, что уже копируется. Файлы малы, копировать «на ходу» можно.
- Перенос между средами: «скачать из админки одной среды и загрузить в другую». Автоматической синхронизации нет.

## 10. Админка: перезагрузка и применение

Раздел «Конфиг метаданных» (только суперпользователь), действия:

1. **Скачать** активный конфиг как `.toml`.
2. **Загрузить или вставить текст** (редактор CodeMirror уже есть в проекте). Загрузка конфиг сразу не применяет.
3. **Проверить и показать отличия.** Отчёт: что добавлено, изменено, помечено `deprecated`, исчезло; для исчезнувших ключей число записей, где они встречаются.
4. **Активировать** только после проверки и явным нажатием. Создаётся новая редакция, предыдущая остаётся в истории.
5. **Откатить** на предыдущую редакцию.
6. **Сбросить из `default.toml`** как отдельное действие с таким же сравнением и подтверждением.

Каждое применение пишется в `journal.jsonl` (кто, когда, какая редакция).

Применение конфига в формах `TbItem` и `TbOffer`:

1. `get_form()` читает активный конфиг и добавляет виртуальные поля (`choice` даёт `ChoiceField`, `bool` даёт `BooleanField` и т. д.).
2. Начальные значения берутся из `j_item_metadata` или `j_offer_metadata` объекта.
3. Небольшой JS показывает и скрывает группы и поля по `when`. Проверка на сервере повторяет условия: скрытые поля не проверяются.
4. В `save_model()` значения виртуальных полей записываются обратно в JSON, а ключи, неизвестные конфигу, сохраняются без изменений.
5. Исходное JSON-поле (CodeMirror) остаётся доступным как «сырой» режим.

## 11. Устойчивость к ошибкам

- **Безопасная деградация.** Если активный конфиг не читается или не проходит проверку, работает последняя корректная редакция. Если корректной нет совсем, админка показывает обычный JSON-редактор. Сайт не падает из-за ошибки в конфиге.
- **Проверка на входе.** Некорректный конфиг активным не станет: проверка перед активацией.
- **Конкурентная правка.** См. п. 9.3, шаг 2.
- **Неизвестные ключи не теряются** при сохранении формы (`metadata_forms_manifest.md`, п. 4).

## 12. Дополнительные идеи (взять или отложить)

- **`aliases` у значения.** Синонимы для парсеров и импорта (`["smoke", "дымчатый"]`): парсер приводит название из источника к стабильному ключу. Связывает конфиг с `parser_architecture.md`, но схема парсеров в конфиг не входит.
- **`inherit = true` у поля формы оффера.** Если значения нет в `j_offer_metadata`, показывается значение из `j_item_metadata` (формализует «Fallback Cascade» из `metadata_architecture.md`).
- **Группы полей** (`group = "appearance"`) превращаются в `fieldsets` админки.
- **`default`** значение по умолчанию.
- **Команды управления** `export_metadata_config`, `import_metadata_config --dry-run`.
- **Отчёт о «сиротах»**: ключи вне конфига и значения, которых нет в `values` (без `allow_other`). Ничего не удаляет.

## 13. Порядок реализации

1. Загрузчик: `tomllib` плюс проверка схемы поверх `default.toml`. Без админки. Тесты на разбор и проверку.
2. Файловое хранилище: чтение `ACTIVE`, кэш по `os.stat`, запись по алгоритму п. 9.3, начальное заполнение из `default.toml`, настройка `METADATA_CONFIG_DIR`. Тесты на гонки записи (два потока) и на оборванную запись (нет `ACTIVE`, нет `default.toml`).
3. Раздел админки: скачать, загрузить, проверить, активировать, откатить, сбросить.
4. Виртуальные поля в формах `TbItem` и `TbOffer`.
5. Отчёт «ключи вне конфига» и команда переименования ключа с `--dry-run`.

Шаги 1–3 уже дают главное: единый реестр, который можно менять без выкладки кода.
